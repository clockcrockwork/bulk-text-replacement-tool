# 大きな入力の扱い（resource policy）

取り込む入力の大きさの上限と、ブラウザへ保存しきれないときの扱い。issue #19 で実測してから
決めた。値は `src/lib/inputLimits.ts` にあり、ここが根拠の正本。

## 決めたこと

| 項目 | 値 | 種類 |
| --- | --- | --- |
| 1ファイルの上限 `MAX_INPUT_BYTES` | 5MiB（decode 前のバイト数） | hard cap（確認で突破できない） |
| 1回の取り込みの合計 `MAX_IMPORT_TOTAL_BYTES` | 5MiB | hard cap |
| 保存の確認の目安 `STORAGE_CONFIRM_CODE_UNITS` | 4Mi（4,194,304）コード単位 | 確認（続行できる） |
| ワークスペース全体の上限 | 設けない | — |
| 保存方式 | localStorage のまま | — |

- **ローカルのファイルと GitHub の取り込みで同じ値を使う。** 経路で扱いを分けると、同じファイルが
  入れ方によって取り込めたり取り込めなかったりする。
- **判定は decode する前のバイト数で行う**（`File.size`、tree の `size`、読みながら数えた長さ）。
  文字数で数えるには全文を文字列にする必要があり、判定のためだけに大きな入力のコピーを作ることになる。
- **上限は hard cap にする。** 「続ける」で取り込めるようにすると、押した時点でタブが応答しなくなるか
  落ちる。確認のあとに取り消す手段が残らない。
- **保存の確認は別に入れる。** localStorage の容量はブラウザごとに違うので、上限ではなく事前の確認にする。
  最終的に保存できたかは `saveWorkspace` の成否で決まり、失敗すれば今までどおり出したままの警告になる。

## どこで判定するか

| 経路 | 1ファイルの上限 | 1回の合計 | 保存の確認 |
| --- | --- | --- | --- |
| ローカルのファイル（選択・ドロップ） | `planFileImport`：読む前に `File.size` で外し、名前を知らせる | 合計が超えたら1件も読まない（どれを残すかを決められないため） | 反映の直前 |
| GitHub（1件） | 一覧で `tooLarge`（size が分かる場合）／`getBlob` が読みながら打ち切る（size が null の場合） | — | 「入力に追加」「更新」の直前 |
| GitHub（一括） | 同上。1件でも超えたら全体を失敗にする（入力は変えない） | 計画の画面で分かっている合計が超えたら取得させない／並行する取得で予算を共有し、届いた分ずつ差し引いて超えたら全部止める | 確定の直前 |
| 表のファイル（表から読み込み） | 読む前に `File.size` で断り、ダイアログの中で名前を知らせる（全文を入力欄に載せて打鍵のたびに解析し直すため） | —（1ファイルだけ） | —（ルールの反映は取り込みの確認とは別） |

- `getBlob` は `Content-Length` が上限を超えていれば本文を読まずに断る。上限内でも信用はしない
  （圧縮されていれば展開前の長さで、無いこともある）。本文はストリームで読みながら数え、上限を超えた
  時点で `reader.cancel()` して打ち切る。
- 一括の合計は、並行する取得（4本）すべてで共有する予算にし、届いた分ずつ差し引く（`BlobReadLimit.take`）。
  読み終えてから合計を足すと、超えたと分かるまでに並行する取得がそれぞれ上限近くまで読めてしまう。
  超えたら全部の取得を中断するので、操作全体で受け取る量は予算と、各取得がその時点で受け取っていた
  1回分までに収まる。
- 取り直しを避けるための blob の控え（`fetchBatchCandidates` の `cache`）は、読み切れた blob だけを持つ。
  始める時点で今回の計画に無い控えは捨て、上限超えのようなやり直しても変わらない失敗なら今回足した
  控えも捨てる（通信の失敗なら残し、再試行で取り直さない）。選び直しを繰り返しても、控えは1回の
  取り込みの量を超えて積み上がらない。
- 上限超えは、やり直しても結果が変わらないので「再試行」を出さない（「閉じる」だけ）。
- 保存の確認は、反映する action をいまの状態に当ててみて（reducer は純粋）、保存する JSON の長さ
  （キー込み・UTF-16 のコード単位）で判定する。本文の文字数と取り込むバイト数を足すような、単位の
  違う値の足し算はしない。改行や引用符はエスケープで長くなるので、文字数では足りない。

## 対象にしないもの

- **作業データ（バックアップ）の読み込み。** 書き出した作業データは複数の入力をまとめた復旧用の
  データで、ファイル全体に 5MiB を掛けると、各入力は上限内なのに正当に書き出したものを読み戻せない
  ことがある。「書き出した正当なワークスペースを読み込めなくしない」（round-trip）を崩さないため、
  今は上限を掛けていない。別の上限が要るなら、値と round-trip の条件を決めてから足す。
- **全画面エディタへの手入力・貼り付け。** ファイルの取り込みではないので、今回の上限の対象外。
- **表示・変換の軽量化**（プレビューを先頭だけにする、ハイライトの `<mark>` の数の上限、置換の断片の
  持ち方）。上限とは別の issue で扱う。**上限を 5MiB より上げるときの前提条件**になる。

## 実測（Chromium, issue #19）

main `4cf6c91` を `vite preview` で配信し、Linux コンテナ（4 vCPU / 15GB）の Chromium 141 で測った。
全部の表と計測条件は [issue #19 のコメント](https://github.com/clockcrockwork/bulk-text-replacement-tool/issues/19#issuecomment-5865795036) にある。
メモリに余裕のあるデスクトップの値なので、スマートフォンでは時間はもっと長く、クラッシュはもっと
小さい大きさで起きる前提で読む。

抜粋（ローカルのファイル、当たりの少ないルール。「最長」はその間タブが応答しない時間）:

| 入力 | 大きさ | 取り込み→表示（最長） | 変換＋ハイライト（最長） | 保存 | レンダラー RSS |
| --- | --- | --- | --- | --- | --- |
| 日本語 UTF-8 | 5MB | 2.8s（2.5s） | 2.7s（2.6s） | ✅ | 0.8GB |
| 日本語 Shift_JIS | 5MB | 3.9s（3.6s） | 3.9s（3.8s） | ✅ | 1.1GB |
| 日本語 Shift_JIS | 10MB | 8.5s（8.0s） | 6.8s（6.7s） | ❌ | 1.8GB |
| 日本語 UTF-8 | 20MB | 10.9s（10.4s） | 9.2s（9.1s） | ❌ | 2.3GB |
| 日本語 Shift_JIS | 100MB | 107.8s（97.1s） | 240 秒以上応答なし | ❌ | 12.8GB |

- decode は重くない（Shift_JIS 100MB でも 1.8 秒）。時間の大半は、全文を `<textarea>` に載せる描画、
  ハイライトの DOM、置換の断片のオブジェクトにかかる。
- localStorage に入るのは、Chromium で 5,242,862 コード単位まで（ASCII 5MB で超える）。
- GitHub から ASCII 100MB を取り込むとレンダラーがクラッシュした。以前の上限（`MAX_BLOB_BYTES` =
  100MB、GitHub の blob API の境界）は安全に扱える大きさを表していなかった。

5MiB にした理由:

- 実際の原稿は十分に収まる（日本語の長編 30 万字で約 0.9MB、100 万字でも約 3MB）。
- 5MB までなら、デスクトップの Chromium で止まる時間が数秒で済む。10MB では取り込みで最大 8 秒、
  当たりの多いルールの変換で 21 秒止まり、保存できない場合も出る。
- ASCII は 5MB でちょうど localStorage に入らなくなるので、保存の上限ともほぼ揃う。

## Safari / iOS

実機での計測は、5MiB の初期値を決める条件にはしていない（Chromium の時点で十分保守的に下げた）。
iOS の実測は「5MiB でもさらに下げる必要があるか」を確かめる release validation として扱う。
**上限を 5MiB より上げる判断は、iOS の実測なしではしない。** 手順（ファイルの作り方、Web インスペクタの
タイムラインで見る項目、localStorage の上限を調べるコード、記録の表）は issue #19 のコメントにある。

## 値を変えるとき

- `src/lib/inputLimits.ts` の値と、`inputLimits.test.ts` の固定値を合わせて変える。
- 上げるなら、先に表示・変換の軽量化を入れ、Chromium と iOS の両方で測り直してこのページを更新する。
- 画面の文言（「5MiB を超えるため…」）は `formatLimit` から作っているので、値を変えれば追従する。
  E2E（`e2e/inputLimits.spec.ts`・`e2e/github.spec.ts`）は値を直接書いているので直す。
